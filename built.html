01 — Distributed systems & media infrastructure

The two biggest builds

Both are separate products with their own domains, their own databases and their own deploy pipelines. Both are open to anyone — no account required to look around.

DirHaven

Live
A search engine and streaming layer for the open web's media.

The open internet is full of unindexed public file directories — terabytes of video, audio, books and images that no search engine meaningfully reaches. DirHaven crawls them, classifies what it finds, and makes it searchable and streamable from one interface. It reads the formats in-browser too: video and audio stream over HLS, PDFs and EPUBs render inline, images gallery.

The hard part

Crawling hostile, inconsistent, frequently-dead sources at scale without the index rotting. That meant a full-text search layer over a large corpus, a content classification pipeline, health monitoring that detects when a source goes stale, and streaming that tolerates origins which were never built to be streamed from.

Vintinuum

Live
A self-hosted AI system with persistent state you can inspect.

Most AI products are a stateless chat box in front of someone else's API. This one runs on my own hardware, with its own database, and keeps continuous state between sessions — memory, an internal model of the person it's talking to, and metrics that change over time. The unusual part is that it's fully observable: you can open its internals and watch what it stored, what changed, and why.

The hard part

Persistence and orchestration, not prompting. A 197-table schema, a routing layer that sends work to local models or cloud models based on what the task actually needs, background jobs that run continuously, and a public site on a CDN talking to a private home server over an authenticated tunnel.

DirMegle

Live
Random-pairing video chat between strangers.

Two people who have never met are connected to each other's cameras in a couple of seconds, with a "next" button that has to re-pair instantly. Its own domain, its own signalling infrastructure.

The hard part

WebRTC peer negotiation through NAT, a matchmaking queue that stays fast while people join and abandon constantly, and teardown that never leaks a session — a dropped peer must not strand the person still waiting.

DirRM Player

Live
One media player used by every surface in the stack.

Give it a URL — a video file, an audio file, a stream, a YouTube link — and it plays it. Four window modes (full, mini, picture-in-picture, theater), each draggable and resizable by the user. It exists because the alternative was five half-working players drifting apart across five products.

The hard part

Building one embeddable component with a stable contract that every other surface can call, so playback behaviour is fixed once and inherited everywhere — and making it survive embedding policies that actively refuse to cooperate.

05 — Engineering practice

How it actually runs

The infrastructure underneath all of the above. I own every layer of it — there is no platform team behind me.

Deployment

Push to main, live in about a minute. Static frontends on a CDN; backends on a process manager with restart-on-failure and health checks. Main is treated as production, because it is.

Public site, private server

The frontend is public and static. The API runs on hardware in my house and is exposed through an authenticated tunnel — no inbound ports, no origin IP on the internet, TLS terminated at the edge.

Data

A 197-table SQLite schema under the main system, with full-text search indexes, migrations and scheduled backups. One authoritative path to the database — an earlier two-copy setup drifted and cost me real hours, so I removed the choice.

Concurrency

Multiple agents work the same repository simultaneously in isolated git worktrees, with a lock discipline and a merge gate. Parallel throughput without stepping on each other was a design problem, not a default.

Cost control

Inference routes to local models where quality holds and to cloud models only where it doesn't. The routing decision is per-task, measured, and the fallback is a deliberate choice rather than a failure.

Interface discipline

One rule I do not break: nothing overlaps anything. Every surface is verified at 320, 375, 768, 1280 and 1920 pixels, with long strings and empty states, before it ships. This page included.
